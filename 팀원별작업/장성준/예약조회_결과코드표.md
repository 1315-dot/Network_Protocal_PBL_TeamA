# 예약 조회 결과 코드표

담당: 장성준 / 기능: `GET /api/v1/reservations/{reservationId}`

> **주의**: `1001 INVALID_REQUEST`, `1004 INVALID_TOKEN`, `9001 INTERNAL_SERVER_ERROR`는 김세훈 담당 명세를 따른다. `3010 RESERVATION_NOT_FOUND`, `3011 RESERVATION_FORBIDDEN`은 예약 조회 담당자의 잠정 제안이며 통합 시 중복 여부를 확인한다.

## 1. HTTP 상태 및 resultCode

| HTTP 상태 | resultCode | message | 발생 상황 | 앱의 처리 |
|---|---:|---|---|---|
| `200 OK` | `0` | `SUCCESS` | 예약 조회 성공 | `data`에 담긴 주차면·시간·상태 표시 |
| `400 Bad Request` | `1001` | `INVALID_REQUEST` | URL의 예약 ID가 UUID 형식이 아님 | 예약 ID 확인, 잘못된 요청 수정 |
| `401 Unauthorized` | `1004` | `INVALID_TOKEN` | 인증 토큰 누락·만료·오류 | 재인증 요청 후 필요 시 다시 조회 |
| `403 Forbidden` | `3011` | `RESERVATION_FORBIDDEN` | 예약은 있으나 현재 사용자에게 접근 권한이 없음 | 접근 불가 안내, 본인 예약 목록 확인 |
| `404 Not Found` | `3010` | `RESERVATION_NOT_FOUND` | 해당 ID의 예약이 존재하지 않음 | 예약 목록 새로고침, ID 확인 |
| `500 Internal Server Error` | `9001` | `INTERNAL_SERVER_ERROR` | 서버 내부 처리 중 오류 발생 | 잠시 후 재조회, 반복 시 서버 로그 확인 |

- `resultCode`는 팀 규칙의 영역을 지킨다: 1000~1999 공통·인증, 3000~3999 예약, 9000~9999 서버 오류.
- 실패 JSON은 항상 `data: null`로 통일한다.
- 모든 HTTP 응답은 요청받은 `X-Request-ID`를 응답 헤더에 그대로 반환한다.
- 개인 예약 정보 노출을 방지하려면 **권한 없음과 예약 없음 모두 `404`로 통일하는 대안**도 고려할 수 있다. 위 표는 학습·설명상 구분한 설계안이므로 팀에서 하나를 선택해야 한다.

## 2. 오류 JSON 예시

### 잘못된 예약 ID — 400 (공통 입력 오류)

```json
{
  "resultCode": 1001,
  "message": "INVALID_REQUEST",
  "data": null
}
```

### 토큰 없음·만료 — 401

```json
{
  "resultCode": 1004,
  "message": "INVALID_TOKEN",
  "data": null
}
```

### 접근 권한 없음 — 403

```json
{
  "resultCode": 3011,
  "message": "RESERVATION_FORBIDDEN",
  "data": null
}
```

### 예약 ID에 해당하는 예약이 없음 — 404

```json
{
  "resultCode": 3010,
  "message": "RESERVATION_NOT_FOUND",
  "data": null
}
```

### 서버 내부 오류 — 500

```json
{
  "resultCode": 9001,
  "message": "INTERNAL_SERVER_ERROR",
  "data": null
}
```

## 3. 서버·클라이언트 대응 원칙

1. 오류가 발생하면 서버는 오류 원인에 맞는 HTTP 상태와 `resultCode`, `message`, `data: null`을 함께 보낸다.
2. 앱은 HTTP 상태와 `resultCode`를 모두 검사해 조치한다.
3. 조회는 데이터를 변경하지 않으므로 네트워크 오류 이후 동일 ID로 다시 조회할 수 있다. 단, 실패했다고 예약 생성 요청을 새로 보내지는 않는다.
4. 서버는 토큰을 검사한 뒤 예약 소유자를 검증해야 한다. 단순히 예약 ID를 아는 사용자에게 예약 상세 정보를 공개하면 안 된다.

## 4. 팀 검토 항목

- 공통 요청 오류는 인증 담당자의 `1001 INVALID_REQUEST`를 재사용한다.
- 변경·취소 담당자가 사용할 3000번대 오류 번호와 충돌하는지?
- `spaceId`의 UUID 형식을 팀 공통 예시와도 통일했는지?
- 예약 상태 필드(`status`), `carNumber`의 필수 여부가 일치하는지?
- `endTime`(주차 사용 종료)과 `expiresAt`(예약 유효 시각)의 정확한 운영 의미를 확정했는지?
- `403`과 `404`를 구분할지, 보안을 위해 하나로 통일할지?

# A조 네트워크 프로토콜 설계 — 인증 및 예약 생성 메시지 정의표

- **담당자:** 김세훈
- **담당 기능:** 사용자 인증(로그인), 주차 예약 생성
- **통신 프로토콜:** HTTP/1.1 기반 HTTPS/TCP
- **서버 포트:** 443
- **데이터 형식:** JSON (UTF-8)
- **최대 JSON 본문 크기:** 16,384바이트

HTTP 본문은 UTF-8로 인코딩하며, 수신 측은 `Content-Length`에 명시된 바이트 수만큼 읽어 본문의 끝을 판단한다.

# 1. 사용자 인증 메시지

## LOGIN_REQ — 로그인 요청

HTTP 요청 시작 줄: `POST /api/v1/auth/login HTTP/1.1`

| 필드명 | 자료형 / 크기 | 설명 |
|---|---|---|
| `Host` | 문자열 / 31바이트 | 요청 헤더. `parking-reservation.example.com` |
| `Content-Type` | 문자열 / 16바이트 | 요청 헤더. `application/json` |
| `Content-Length` | 정수 값(10진수 문자열) / 최대 5바이트 | 요청 헤더. JSON 본문의 UTF-8 바이트 수 |
| `X-Request-ID` | UUID 문자열 / 36바이트 | 요청 헤더. 요청과 응답을 연결하는 식별자 |
| `userId` | 문자열 / 본문 크기 제한 이내 | JSON 본문. 사용자 아이디 |
| `password` | 문자열 / 본문 크기 제한 이내 | JSON 본문. 사용자 비밀번호 |

### 요청 JSON 예시 — LOGIN_REQ

```http
POST /api/v1/auth/login HTTP/1.1
Host: parking-reservation.example.com
Content-Type: application/json
Content-Length: [본문 바이트 수]
X-Request-ID: 123e4567-e89b-12d3-a456-426614174000
```

```json
{
  "userId": "user123",
  "password": "password123"
}
```

## LOGIN_RES — 로그인 성공 응답

HTTP 응답 시작 줄: `HTTP/1.1 200 OK`

| 필드명 | 자료형 / 크기 | 설명 |
|---|---|---|
| `Content-Type` | 문자열 / 16바이트 | 응답 헤더. `application/json` |
| `Content-Length` | 정수 값(10진수 문자열) / 최대 5바이트 | 응답 헤더. JSON 본문의 UTF-8 바이트 수 |
| `X-Request-ID` | UUID 문자열 / 36바이트 | 응답 헤더. 요청에서 받은 값을 그대로 반환 |
| `resultCode` | 정수 / 숫자 표현 기준 | JSON 본문. 성공 코드 `0` |
| `message` | 문자열 / 7바이트 | JSON 본문. `SUCCESS` |
| `data` | JSON 객체 | JSON 본문. 인증 결과 데이터 |
| `data.accessToken` | 문자열 / 본문 크기 제한 이내 | 발급된 인증 토큰 |
| `data.tokenType` | 문자열 / 6바이트 | 토큰 유형. `Bearer` |
| `data.expiresAt` | UTC 시각 문자열 / 20바이트 | 인증 토큰 만료 시간. `YYYY-MM-DDTHH:mm:ssZ` |

### 성공 응답 JSON 예시 — LOGIN_RES (200 OK)

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: [본문 바이트 수]
X-Request-ID: 123e4567-e89b-12d3-a456-426614174000
```

```json
{
  "resultCode": 0,
  "message": "SUCCESS",
  "data": {
    "accessToken": "발급된 인증 토큰",
    "tokenType": "Bearer",
    "expiresAt": "2026-11-23T14:00:00Z"
  }
}
```

# 2. 주차 예약 생성 메시지

|---|---|---|

| `Authorization` | 문자열 / 최대 2,048바이트 | 요청 헤더. `Bearer `와 로그인 시 발급받은 인증 토큰 |
| `Content-Type` | 문자열 / 16바이트 | 요청 헤더. `application/json` |
| `Content-Length` | 정수 값(10진수 문자열) / 최대 5바이트 | 요청 헤더. JSON 본문의 UTF-8 바이트 수 |

# 3. 메시지 처리 절차

## 3.1 사용자 인증 처리 절차

1. 앱에서 사용자가 아이디와 비밀번호를 입력한다.
2. 앱은 `LOGIN_REQ` 메시지를 HTTPS를 통해 서버로 전송한다.
3. 서버는 요청 형식과 사용자 계정 정보를 확인한다.
4. 인증에 성공하면 `LOGIN_RES` 메시지에 인증 토큰과 만료 시간을 담아 반환한다.
5. 앱은 전달받은 토큰을 저장하고 이후 인증이 필요한 요청에 활용한다.
6. 인증에 실패하면 해당 오류 코드와 메시지를 반환한다.

## 3.2 주차 예약 생성 처리 절차

1. 앱에서 사용자가 주차면과 이용 시간을 선택한다.
2. 앱은 예약 요청에 사용할 `Idempotency-Key`를 생성한다.
3. 앱은 `RESERVATION_CREATE_REQ` 메시지에 인증 토큰과 예약 정보를 담아 서버로 전송한다.
4. 서버는 인증 토큰의 유효성을 확인한다.
5. 서버는 입력값과 `Idempotency-Key`의 사용 여부를 확인한다.
6. 서버는 해당 주차면의 예약 시간 충돌 여부를 검사한다.
7. 예약이 가능하면 예약을 생성하고 `RESERVATION_CREATE_RES` 성공 응답을 반환한다.
8. 앱은 전달받은 예약 정보를 화면에 표시한다.
9. 예약 충돌이 발생하면 `409 Conflict` 응답을 반환하고 앱은 사용자에게 안내한 뒤 최신 주차 현황을 재조회한다.
10. 응답이 지연되어 같은 요청을 재전송하는 경우 기존 `Idempotency-Key`를 유지하여 중복 예약 생성을 방지한다.

# 4. 중복 및 동시 예약 방지 설계

## 4.1 Idempotency-Key를 이용한 중복 요청 방지

- 동일한 `Idempotency-Key`와 동일한 요청 내용이 다시 들어오면 기존 처리 결과를 반환한다.
- 동일한 `Idempotency-Key`에 다른 요청 내용이 들어오면 `409 Conflict`와 `IDEMPOTENCY_KEY_CONFLICT`를 반환한다.
- 동일한 키의 요청이 아직 처리 중이면 `409 Conflict`와 `IDEMPOTENCY_REQUEST_IN_PROGRESS`를 반환한다.
- 응답이 지연되어 재요청하는 경우 앱은 기존 `Idempotency-Key`를 그대로 사용한다.

## 4.2 동시 예약 방지

여러 사용자가 동일한 주차면의 겹치는 시간대를 동시에 예약하는 경우 서버와 데이터베이스에서 예약 충돌을 검사하고 원자적으로 처리한다. 먼저 예약 확정에 성공한 요청만 처리하고 나머지 요청에는 `409 Conflict`와 `SPACE_ALREADY_RESERVED`를 반환한다.

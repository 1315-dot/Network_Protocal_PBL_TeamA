# 김세훈 담당 메시지 명세서
## 로그인·인증 및 예약 생성

- 담당자: 김세훈
- 담당 기능: 로그인, 토큰 인증, 예약 생성
- 전송 방식: HTTPS/TCP
- HTTP 버전: HTTP/1.1
- 서버 주소: `parking-reservation.example.com`
- 서버 포트: `443`
- 데이터 형식: UTF-8 JSON

---

# 1. 공통 통신 규칙

## 1-1. HTTP 요청 헤더

| 헤더 | 필수 여부 | 설명 |
|---|---|---|
| Host | 필수 | 요청 대상 서버 주소 |
| Content-Type | JSON 본문이 있을 때 필수 | 데이터 형식 지정 |
| Content-Length | JSON 본문이 있을 때 필수 | 본문 크기를 UTF-8 바이트로 표시 |
| Authorization | 인증이 필요한 요청에 필수 | 인증 토큰 전달 |
| X-Request-ID | 필수 | 요청을 구분하는 UUID |
| Idempotency-Key | 예약 생성·변경·취소·연장에 필수 | 중복 요청 방지를 위한 UUID |

## 1-2. HTTP 응답 헤더

| 헤더 | 필수 여부 | 설명 |
|---|---|---|
| Content-Type | JSON 응답일 때 필수 | 응답 데이터 형식 |
| Content-Length | JSON 응답일 때 필수 | 응답 본문의 UTF-8 바이트 크기 |
| X-Request-ID | 필수 | 요청에서 전달받은 ID를 그대로 반환 |

## 1-3. JSON 데이터 규칙

| 항목 | 규칙 |
|---|---|
| 문자 인코딩 | UTF-8 |
| 데이터 형식 | JSON |
| 필드 이름 | camelCase |
| 식별자 | UUID 문자열 |
| 날짜 및 시간 | UTC 기준 YYYY-MM-DDTHH:mm:ssZ |
| 수량 | 정수 |
| 참/거짓 | true, false |
| 값이 없는 경우 | null |
| 성공 결과 코드 | 0 |
| 실패 결과 코드 | 4자리 숫자 |

## 1-4. 공통 응답 구조

모든 응답은 다음 세 가지 항목으로 구성한다.

| 필드 | 자료형 | 설명 |
|---|---|---|
| resultCode | Integer | 처리 결과 코드 |
| message | String | 처리 결과 메시지 |
| data | Object 또는 null | 실제 응답 데이터 |

성공 응답 예시:

```json
{
  "resultCode": 0,
  "message": "SUCCESS",
  "data": {}
}
```

실패 응답 예시:

```json
{
  "resultCode": 1002,
  "message": "INVALID_CREDENTIALS",
  "data": null
}
```

※ X-Request-ID와 Idempotency-Key는 HTTP 헤더로 전달하며 JSON 본문에 포함하지 않는다.

# 2. 로그인 및 인증

## 2-1. 로그인 요청

### 메시지 기본 정보

| 항목 | 내용 |
|---|---|
| 메시지 이름 | 로그인 요청 |
| HTTP Method | POST |
| Endpoint | /api/v1/auth/login |
| 전송 방식 | HTTPS/TCP |
| 데이터 형식 | UTF-8 JSON |
| 인증 여부 | 불필요 |
| Idempotency-Key | 사용하지 않음 |

### 요청 헤더 정의

| 헤더 | 값 | 설명 |
|---|---|---|
| Host | parking-reservation.example.com | 서버 주소 |

### 요청 메시지 정의표

```json

  "password": "password123"
```

| 필드명 | 자료형 | 설명 |

| data.refreshToken | String | 토큰 재발급용 토큰 |

| data.expiresAt | String | 접근 토큰 만료 시각 |

```text
    |          |
    |          v
```

## 2-2. 토큰 재발급 요청 (Refresh Token)

※ Refresh Token 방식은 추가 제안 사항이며 팀의 최종 합의 후 적용한다.

### 메시지 기본 정보

| 항목 | 내용 |
|---|---|
| 메시지 이름 | 토큰 재발급 요청 |
| HTTP Method | POST |
| Endpoint | /api/v1/auth/refresh |
| 전송 방식 | HTTPS/TCP |
| 인증 정보 | Refresh Token 필요 |
| Idempotency-Key | 사용하지 않음 |

### 요청 헤더 정의

| 헤더 | 값 | 설명 |
|---|---|---|
| Host | parking-reservation.example.com | 서버 주소 |
| Authorization | Bearer {refreshToken} | Refresh Token 전달 |
| X-Request-ID | UUID | 요청 식별자 |
| Content-Length | 0 | 요청 본문 없음 |

### 요청 메시지 정의표

별도의 JSON 요청 본문 없이 Authorization 헤더로 Refresh Token을 전달한다.

### 토큰 재발급 요청 예시

```http
POST /api/v1/auth/refresh HTTP/1.1
Host: parking-reservation.example.com
Authorization: Bearer REFRESH_TOKEN_VALUE
X-Request-ID: 123e4567-e89b-12d3-a456-426614174000
Content-Length: 0
```

### 성공 응답 메시지 정의표

| 필드명 | 자료형 | 설명 |
|---|---|---|
| resultCode | Integer | 처리 결과 코드 |
| message | String | 처리 결과 메시지 |
| data.accessToken | String | 새 접근 토큰 |
| data.refreshToken | String | 새 Refresh Token |
| data.tokenType | String | 토큰 유형 |
| data.expiresAt | String | 접근 토큰 만료 시각 |
| data.refreshExpiresAt | String | Refresh Token 만료 시각 |

### 토큰 재발급 성공 응답 JSON

```json
{
  "resultCode": 0,
  "message": "TOKEN_REFRESH_SUCCESS",
  "data": {
    "accessToken": "NEW_ACCESS_TOKEN",
    "refreshToken": "NEW_REFRESH_TOKEN",
    "tokenType": "Bearer",
    "expiresAt": "2026-11-23T11:30:00Z",
    "refreshExpiresAt": "2026-12-23T11:00:00Z"
  }
}
```

### 토큰 재발급 처리 다이어그램

```text
[클라이언트]
    |
    | Refresh Token 전달
    v
[서버]
    |
    | Refresh Token 유효성 검사
    |
    +------ 유효함
    |        |
    |        v
    |     새 토큰 발급
    |        |
    |        v
    |     성공 응답
    |
    +------ 유효하지 않음
             |
             v
          오류 응답
```

### 토큰 재발급 결과 코드표

| HTTP 상태 코드 | 결과 코드 | 메시지 | 설명 |
|---|---:|---|---|
| 200 | 0 | TOKEN_REFRESH_SUCCESS | 토큰 재발급 성공 |
| 401 | 1005 | INVALID_REFRESH_TOKEN | 유효하지 않거나 만료된 Refresh Token |
| 500 | 9001 | INTERNAL_SERVER_ERROR | 서버 내부 오류 |

# 4. 중복 예약 요청 처리 규칙

예약 생성은 같은 요청이 반복 전송되더라도 중복으로 예약되지 않도록 처리해야 한다.

이를 위해 Idempotency-Key를 사용한다.

| 상황 | 서버 처리 |
|---|---|
| 동일한 키와 동일한 요청 내용 | 이전 처리 결과 반환 |
| 동일한 키와 다른 요청 내용 | 3004 오류 반환 |
| 동일한 키의 요청이 처리 중 | 3005 오류 반환 |
| 서로 다른 키로 같은 공간을 동시에 예약 | 예약 가능 여부를 확인하고 하나의 요청만 성공 처리 |

예약 데이터가 동시에 생성되는 문제를 방지하기 위해 서버에서는 예약 가능 여부 확인과 예약 등록이 원자적으로 처리되도록 한다.
